推理服务的瓶颈

vLLM 是面向大模型推理与服务的引擎，目标是在同一批权重上同时服务更多请求。主要瓶颈在显存容量、KV 缓存与调度：整段 prompt 先做一次前向（prefill），随后每步只推进一个 token（decode）。

对外是 OpenAI 兼容的 HTTP 服务，内部各角色的分工见后文的结构一节。

KV 缓存

生成分两步。整段 prompt 先一次前向算完，这一步叫 prefill，计算密集。之后每轮只推进一个 token，叫 decode，每步都要读取这条序列此前所有位置的键与值，访存密集。

K 与 V 指注意力里缓存的键与值。缓存省掉的是对已知位置的重复计算，每步仍要读这些缓存做注意力；代价是显存，且随上下文线性增长。下式给出每个 token 的 KV 字节数：

容量浪费来自按最大上下文为请求预留显存。连续预分配会留下大量可能用不到的空间，也会产生分配碎片。

分页把显存切成等大的块，块池统一分配，请求只持有块表，记录第 i 个逻辑块落在哪个物理块。物理块随意分配，同一序列的块不必相邻；两张块表指向同一格，就是共享。

前缀缓存

多轮对话与批量评测里，请求共享同一段开头，这段 KV 算一次就够。判断“同一段”不能只比块内 token：块哈希把本块 token、父块哈希与额外字段（LoRA id、多模态哈希）合在一起，父哈希把链串起来，所以只有从头每块都对上才命中。

只缓存写满的块，半块会被后续 token 改写。共享块用引用计数守住，计数不归零不能淘汰；计数归零的整块可能仍留在缓存里等待复用，直到被最近最少使用策略淘汰。

前缀缓存复用匹配的 KV，计数归零的块可被淘汰，代价是哈希、查表与管理开销。

连续批处理

槽位是这一轮最多能并排处理的请求条数，上限取决于序列长度、token 预算、KV 占用、模型显存与配置，不是单纯由块数决定。下面是一个受控对比：同一组请求、同样到达时刻、同样 3 个槽位，只有准入规则不同。

静态批处理指组批时定下成员、之后不再变，整批一起推进，直到最慢的那条结束。做完的请求仍占着槽位，新到的只能等下一批。批里只要有一条长尾，其余槽位就空到那条结束。

连续批处理每轮重新组批：做完的立刻退出并归还块，排队的补进来。把长 prompt 切成多块（chunked prefill）与 decode 同批计算是另一项策略，可以与连续批处理叠加，但不是连续批处理的定义。

常见的预算顺序是 decode 优先：先把待解码的排进这一轮的 token 预算，剩下的给 prefill。这样计算密集的 prefill 与访存密集的 decode 可能落在同一批里，算力与带宽同时被利用。

分页让这种调度更容易实现：上下文可以散在任意块里，这一轮把哪些请求拼在一起只需选择读取哪些块表，不必搬移整段数据。

块池耗尽时，新请求排不进来，运行中的请求也需要新块写 KV。做法是抢占：挑一条请求，释放其块，退回等待队列，等有空间再从该请求的前缀重算。V1 默认重算而不是换出到内存，因为在该实现中重新 prefill 通常比写出再读回更划算。

代价是延迟，被抢占的请求要重新 prefill。频繁抢占通常说明并发需求超过显存容量，也可能是调度策略与预算设置的结果。

量化与并行

量化

量化是减少每个数值占的 bit 数。常见部署以 fp16 存储权重与 KV，每个数 16 位浮点；量化换成 fp8（8 位浮点）、int8 或 int4（8 位、4 位整数）。从 16 位降到 8 位，每个权重占的字节减半；降到 4 位再减半。

降低位宽能减少存储与访存字节。decode 一步只算一个 token，算术强度低，往往受显存带宽限制；增大批处理可以提高权重复用。收益取决于 kernel、硬件与任务，位宽减半不必然让一轮时间减半。

量化改变权重精度，输出可能随之改变，位宽越低差别通常越大。是否可接受取决于任务的误差要求，需要在目标数据上评估。

并行

一些时候需要使用多张显卡：一张卡放不下模型，就得让每张卡只存一部分权重，也就是模型并行；模型放得下但吞吐不够，就在每组设备上放一份完整副本，也就是数据并行。

模型并行有三种分法。张量并行把权重或计算按头、通道切开，各卡算一部分，并通过集合通信汇总，切得越细通信越频繁，通常在一台机器内使用。流水线并行按层分段，可以跨机器，代价是流水线气泡。MoE 模型还有专家并行，把不同专家放到不同卡上。

数据并行让每组卡持有一份完整副本，各自调度请求，吞吐随副本增多而上升。每组副本内部仍可使用张量并行或流水线并行，因此不要求每张单卡都放下整个模型。

手段 分什么 换来什么 代价
张量并行 权重或计算按头、通道 每卡权重变小，腾出的显存进块池 集合通信开销
流水线并行 按层分，可跨节点 单卡权重变小 流水线气泡
专家并行 MoE 的专家 单卡专家显存变小 路由与负载均衡开销
数据并行 每组卡一份完整副本 提高并发服务能力；每组持有完整模型 每组副本的显存与通信开销

前三种把单卡权重或计算切开，数据并行在每组副本内保留完整模型。并行主要解决装不下与吞吐不足；不同切分方式下，每 token 的数据移动与通信开销不同。

vLLM 的结构

以下按 V1 架构介绍进程角色，实现细节以官方架构文档为准。

API server

API server 处理文本输入与输出。收下 OpenAI 兼容的 HTTP 请求，套 chat 模板、分词成 token id，连同采样参数打包交给 EngineCore；反向把回来的 token id 解码成文本，按 SSE 推给客户端。显存与调度不由 API server 管理。

分词、图片解码与流式返回都消耗 CPU。CPU 侧成为瓶颈时，可先评估增加 API server，再考虑其他扩容方式。

EngineCore

EngineCore 不处理文本，也不执行模型前向；EngineCore 管理调度器与 KV 缓存管理器，块池、块表、前缀哈希都在后者这里，并协调各 worker。

主循环按轮推进，每一轮依次做四步：

  1. 从等待队列挑出这一轮要算的请求，按预算排进 decode 与 prefill。
  2. 向 KV 管理器查前缀能复用哪些块，再按需分配新块。
  3. 把这一轮拼成批次，带每个请求的块表交给 worker。
  4. 收回采样结果，决定下一轮。

一个数据并行 rank 配一个 EngineCore；同一份模型用张量并行或流水线并行摊到多卡时，也由 EngineCore 协调那几个 worker。CPU 核数不足会拖住每轮决策。

GPU worker

每张显卡由一个 worker 进程管理：加载所属的权重分片，管理该卡显存，执行前向。每个 worker 里有一个 model runner，负责把这一轮的输入张量准备好、按块表读 KV、执行 attention 与 FFN。采样由持有相应 logits 的 rank 完成，结果以 token id 回传。

worker 管理该卡显存中的三份内容：权重、前向时的激活与 CUDA graph 预留、KV 池。CUDA graph 把一轮前向要下发的 GPU 指令记录下来。之后遇到匹配的批次形状与执行键就重放，省掉逐算子下发的开销。形状不匹配时可以重新捕获，也可以回退到即时执行；显存因此要单独预留。

一次请求的完整链路

假设系统提示加用户问题共 1800 个 token，其中前 1200 个与一条仍在缓存中的旧请求完全相同。

  1. API server 收到请求，分词成 1800 个 token id，连同采样参数打包，经 ZMQ 交给 EngineCore。
  2. 调度器把请求放进等待队列，等这一轮的 token 预算。
  3. KV 管理器对前 1200 个 token 逐块算哈希，命中 75 个块（块容量 16 token），引用计数加一，不重算。
  4. 余下 600 个 token 进入 prefill；此时还有别的请求在 decode，按本轮 token 预算分片推进。
  5. prefill 写新的 KV，按需向空闲队列要块；末块写不满也占一整块，位置记进块表。
  6. 这一轮的批次带着各自的块表下发到每个 GPU worker，worker 按块表读 KV、算 attention、得 logits。
  7. 采样出下一个 token id，回传 EngineCore，再交给 API server；API server 解码成文本、流式推给客户端。这个 token 的 K、V 在下一轮前向时写进最后一个块。
  8. 之后每轮重复第 5 到第 7 步，直到结束符或长度上限。
  9. 请求结束，块表作废：共享的前缀块计数减一，计数归零后仍可能留在缓存里等待复用；其余块释放，是否立即淘汰由缓存策略决定。
